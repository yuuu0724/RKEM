# 芯片视觉与在岗检测系统

# 摘要

本作品面向嵌入式工业检测与现场人员状态管理场景，围绕芯片来料或工位槽位检测、员工签到签退、疲劳告警和数据上传等需求，构建了一套运行在 RK3588 Linux 平台上的一体化检测系统。系统以两路摄像头作为主要输入，其中 `/dev/video21` 用于芯片字符识别与表面缺陷检测，`/dev/video23` 用于员工疲劳状态检测；主程序 `main_process` 集成 Qt Widgets 人机界面、OpenCV 图像采集、RKNN 模型推理、串口通信、SQLite 本地考勤记录、HTTP 数据上传和音频告警。算法侧使用 PP-OCRv5 RKNN 检测/识别模型完成芯片字符读取，并通过字符归一化与最长公共子序列模糊匹配判断芯片型号是否符合模板；缺陷和疲劳检测使用 YOLO 类 RKNN 模型，缺陷标签包括 `pin_damage` 和 `scratch`，疲劳标签包括 `close_eye`、`open_eye`、`open_mouth`。系统在 HMI 中以 1×4 槽位流程组织检测，按照“字符匹配通过且无缺陷”为良品的规则更新良品数、次品数和良品率，并通过默认 `/dev/ttyS8` 串口向运动下位机发送前进、回退和自动运行命令。员工管理通过默认 `/dev/ttyS9` 串口与外部人脸/指纹识别设备通信，使用带帧头、命令码、长度、CRC16 和帧尾的二进制协议完成新建员工、签到、签退和删除，并将本机记录保存到 SQLite 数据库。当前代码已形成可运行的 Qt 集成入口、模型加载与推理链路、硬件串口协议、日志和上传框架；PCA9685、I²C、GPIO、PWM 等低层舵机接口未在代码中体现，机械执行结构需要结合实物继续补充。作品适合作为小型产线视觉检测、嵌入式 AI 联调和人机协同管理的工程样机。

关键词：RK3588；工业视觉；OCR；缺陷检测；疲劳检测；Qt HMI

# 第一部分 作品概述

## 1.1 功能与特性

系统围绕“芯片检测 + 员工在岗管理”展开。现场人员在 HMI 中输入芯片字符模板，系统启动 `/dev/video21` 图像采集，调用 OCR 模型识别芯片丝印字符，同时调用缺陷模型检测引脚损坏、划痕等异常；识别结果进入 1×4 槽位判定流程，字符模糊匹配通过且未检测到缺陷时判为良品，否则判为次品，并实时更新 KPI。第二路 `/dev/video23` 摄像头持续执行疲劳检测，结合闭眼、张嘴、PERCLOS 和持续时间规则触发“疲劳/严重疲劳”告警。系统还提供员工新建、签到、签退、删除和考勤记录查看，并通过串口控制下位机运动。

## 1.2 应用领域

从代码功能看，作品适用于小批量芯片或电子元件的字符核验、表面缺陷初筛和工位人员状态管理。它更接近产线边缘端检测终端，而不是完整 MES 或大型视觉平台：能够在本机完成摄像头采集、NPU 推理、槽位结果显示、串口联动和记录上传，但数据库统计、权限管理、远程配置和机械闭环定位仍需继续完善。该系统也适合嵌入式 AI 教学、RKNN 模型部署验证、工业相机/USB 摄像头联调、员工识别设备协议调试等场景。对于高速产线和精密分拣应用，需要补充标准测试集、稳定光源、机械定位精度和连续运行数据。

## 1.3 主要技术特点

软件采用 C++17，核心入口为 `cpp/src/hmi_main.cc` 和 `cpp/src/hmi_mainwindow.cc`，界面使用 Qt Widgets 与 QtSql，算法调用 RKNN Runtime，图像处理依赖 OpenCV 和 Rockchip RGA 库。主 HMI 不是单纯显示层，而是直接集成摄像头预览、OCR 线程、YOLO 推理线程、串口线程、数据库和上传线程。NPU 分配在代码中明确：OCR 检测和识别绑定 Core 0，疲劳模型绑定 Core 1，缺陷模型绑定 Core 2。摄像头 1 通过 `camera_capture_service` 写入临时帧文件隔离 V4L2 采集，摄像头 2 直接使用 `cv::VideoCapture`。硬件通信以串口为主，员工设备和运动下位机分别使用独立串口，协议解析、超时和回包处理集中在 HMI。

## 1.5 主要创新点

1. 将芯片字符核验、缺陷检测、员工疲劳检测和考勤管理统一到 `main_process` 一个现场入口，减少多程序联调成本。
2. 使用 RK3588 三个 NPU Core 分配不同模型任务，代码层面对 OCR、疲劳和缺陷模型做了明确隔离。
3. HMI 将检测结果按 1×4 槽位组织，并与运动下位机串口回包联动，形成“到位-识别-判定-移动”的流程。
4. 疲劳检测不只显示模型标签，还叠加闭眼持续时间、张嘴事件、5 分钟事件统计和 60 秒 PERCLOS 判定。
5. 员工管理同时包含外设协议、SQLite 本地记录和远程上传接口，便于后续接入真实人员识别设备。

## 1.6 设计流程

# 第二部分 系统组成及功能说明

## 2.1 整体介绍

系统整体由输入、核心处理、算法、数据、通信、输出执行和用户交互七类模块组成。输入层包括芯片检测摄像头 `/dev/video21`、疲劳检测摄像头 `/dev/video23`、员工识别外设串口 `/dev/ttyS9` 和运动下位机串口 `/dev/ttyS8`。核心处理层是 `main_process` 中的 `MainWindow`，它负责启动摄像头预览、OCR 线程、YOLO 检测线程、串口接收线程、数据库连接和云端上传线程。算法层包含 `HmiOcrDetector` 和 `InspectionYoloDetector`，分别完成 OCR 推理和 YOLO 后处理。数据层保存员工档案、考勤记录、日志和上传队列。输出层包括 HMI 状态显示、槽位良次品结果、串口运动命令、音频告警和 HTTP 上传。

数据流为：摄像头图像进入 OpenCV，转换为 RGB/灰度后缩放到 640×640；芯片图像送入 OCR 和缺陷模型，结果经模板匹配和缺陷规则融合后更新槽位；疲劳图像送入疲劳模型，再经时间窗口规则生成告警。控制流为：用户输入模板后触发检测，系统消费到位请求，完成当前槽位识别后调用 `sendMoveCommand()`，串口收到运动完成或回退完成回包后继续下一槽或结束一轮。异常处理主要通过界面状态、日志、串口超时、模型加载失败提示和上传失败日志完成。

### 2.2.3 电路各模块介绍

电路连接从代码可确认的部分主要包括摄像头、串口、音频和网络。芯片检测摄像头固定使用 `/dev/video21`，HMI 对该路相机采用独立 `camera_capture_service` 进程采集帧文件，降低模型库与 V4L2 直接抢占的影响；疲劳相机 `/dev/video23` 在 HMI 内直接打开，并对该设备优先按 YUYV 格式处理。员工设备串口默认 `/dev/ttyS9`，电机/运动下位机串口默认 `/dev/ttyS8`，均配置为 115200 波特率、8 数据位、1 停止位、无校验，并在 `serial_port.cc` 中设置原始模式，避免二进制帧被终端行规程转换。

员工管理协议帧格式为 `AA 55 + command + length(2B) + payload + CRC16(2B) + FF`，CRC 从命令码到数据区计算。运动短帧兼容 `AA 55 command FF`，已定义命令包括前进 `0x20`、完成 `0x21`、回退完成 `0x22`、中断 `0x23`、自动运行 `0x24`、按距离前进 `0x25`、按距离回退 `0x26`。代码未出现 I²C 总线号、`0x40` 设备地址、PCA9685 PWM 频率或舵机脉宽参数，相关电路需后续根据实物和下位机代码补充。

#### OCR 识别与模板匹配模块

* 功能说明：对芯片图像进行 PP-OCRv5 检测与识别，并将识别文本与用户模板进行模糊匹配。

* 核心类或函数：`HmiOcrDetector::init()`、`recognize()`、`normalizeChipText()`、`fuzzyChipMatch()`、`MainWindow::ocrLoop()`。
* 输入变量：灰度 640×640 图像、检测模型 `model/ocr/PP-OCRv5_mobile_det.rknn`、识别模型 `model/ocr/PP-OCRv5_mobile_rec.rknn`、用户模板。
* 输出变量：原始文本、归一化文本、最高置信度、匹配结果。
* 调用关系：`ocrLoop()` 消费到位请求后调用 `recognize()`，再调用 `handleOcrResult()` 更新槽位和上传。
* 异常处理：模型初始化失败时界面显示 OCR 模型加载失败；识别失败时按不匹配处理。
* 当前完成情况：HMI 已接入；旧版 `OcrEngine` 仍有后处理 TODO，主要作为独立子进程骨架保留。

* 异常处理：模型初始化失败时打印错误并停止该检测线程；无检测结果按无缺陷处理。

#### 疲劳检测模块

* 功能说明：检测闭眼、睁眼、张嘴状态，并基于时间窗口规则判断疲劳等级。
* 代码位置：`cpp/src/yolo_detector.cc`、`cpp/src/hmi_mainwindow.cc`、`cpp/src/audio_alert.cc`。
* 核心类或函数：`CameraPreviewWidget::detectionLoop()`、`updateFatigueDecision()`、`setFatigueDecision()`、`AudioAlert::PlayFatigueWarningAsync()`。
* 输入变量：摄像头 2 灰度图、`model/fatigue/fatigue_two_outputs_i8.rknn`、标签 `close_eye/open_eye/open_mouth`。
* 输出变量：检测框、疲劳等级、疲劳分数、告警日志、音频提醒、云端告警。
* 调用关系：YOLO 检测结果先过滤中心区域，再统计 60 秒闭眼样本、5 分钟闭眼/张嘴事件；达到 PERCLOS ≥ 0.30 或事件分数阈值后触发告警。
* 异常处理：疲劳告警 30 秒后自动解除；音频播放失败只记录警告，不阻断检测。
* 当前完成情况：HMI 已接入。

#### 串口通信与员工协议模块

后续应优先补充标准测试集和性能日志，明确 OCR 识别率、缺陷检出率、误报率、推理耗时和连续运行稳定性。机械侧建议补充下位机源码或协议文档，若采用开环运动，需要增加限位、编码器或视觉定位校正，减少多槽位累计误差。视觉侧可增加稳定光源、相机标定、ROI 裁剪和模板管理，降低背景干扰。数据侧可扩展检测记录表、批次统计、导出功能和远程配置。电路侧若后续接入 PCA9685、GPIO、继电器或传感器，应将总线号、地址、通道、供电和保护设计写入代码和文档。

## 4.2 心得体会

从工程实现看，本项目的难点不在单个模型能否跑通，而在多模块同时运行后能否保持节拍一致。芯片检测需要摄像头、OCR、缺陷模型和运动下位机配合：图像太早采集会遇到工件未到位，太晚采集又会拖慢节拍，所以代码采用到位请求和串口完成回包来驱动槽位检测。疲劳检测则是另一类问题，单帧出现闭眼并不一定代表疲劳，因此 HMI 中加入了时间窗口、闭眼持续 400 ms、张嘴持续 1 s、5 分钟事件统计和 PERCLOS 规则，这比直接把模型标签显示出来更接近实际值班场景。

硬件调试上，串口协议的可靠性很关键。项目使用原始串口模式，避免换行转换、回显和软件流控影响二进制帧；员工协议还加入 CRC16 和长度字段，能够识别错误帧。运动控制则同时兼容短帧和带距离参数的帧，便于从简单动作逐步扩展到按毫米距离控制。实际联调时还需要关注串口地线、波特率一致性、下位机回包超时和断电恢复，这些问题往往比算法代码更容易影响整机演示。

软件界面开发体现了嵌入式现场应用的特点：HMI 不能只展示图片，还要把模板设置、良次品规则、报警日志、运动控制和员工管理放在同一个操作流程里。当前 `main_process` 已把这些内容集中到一个入口，避免了多个进程窗口分别操作的混乱。不过，仓库里仍保留了早期独立子进程和旧版 `QtInterface` 占位代码，后续维护时应继续以 `main_process` 为主线，避免功能分散。

模型和算法调试方面，RKNN Core 分配、输入格式、灰度/RGB 转换和输出后处理都需要逐项确认。OCR 模块复用 PP-OCRv5 接口，缺陷和疲劳模块使用统一 YOLO 解码器，并兼容单输出和双输出张量形态，这提高了模型替换的灵活性。后续如果要提交完整作品材料，最需要补的是标准化测试：同一批芯片、多种缺陷、不同光照和不同员工姿态下的识别结果，以及真实运行日志截图。只有把这些数据补齐，报告中的“待实测”才能转化为可验证的指标。
